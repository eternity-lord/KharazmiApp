## ۱) ریشه‌ی باگ (Root Cause) — یک نقطه، اثبات‌شده با probe

در `Kharazmi_Server/routers/teachers.py` (اندپوینت `GET /teachers/{teacher_id}/pending_settlement`) فیلتر تاریخ این‌گونه بود:

```python
def _in_range(value):
    parsed = parse_project_date(value)
    if parsed is None:
        return False          # ← هر مقدار غیرقابل‌parse، از جمله date=NULL
    ...
sessions = [s for s in q_sessions.all() if _in_range(s.date)]
```

`parse_project_date(None)` → `None` → `_in_range` = `False` → جلسه **بی‌صدا** از نتیجه حذف می‌شد — و این اتفاق **حتی وقتی هیچ بازه‌ای هم درخواست نشده بود** (start/end هر دو `None`) رخ می‌داد. پس این رفتار ناخواسته بود، نه فیلتر درخواستی کاربر.

**اثبات زنده (probe، کد قبل از فیکس):** سناریویی با ۶ جلسه‌ی واجد طلب (۳ تاریخ‌دار + ۳ بی‌تاریخ) و ۱ جلسه‌ی تسویه‌شده:

```
session_count: 2   (به‌جای 6)         ← ۴ جلسه حذف شد
total_amount : 150,000  (به‌جای 450,000)  ← ۳۰۰٬۰۰۰ تومان از طلب معلم ناپدید شد
```

جلسه‌های حذف‌شده: `date=NULL`، `date=NULL + هزینه NULL`، `date=NULL + عنوان کلاس NULL`، و تاریخ **invalid غیرNULL** (`999/99/99`).

**اثر واقعی:** طلب معلم و تعداد جلساتش کمتر از واقع نمایش داده می‌شد و در نتیجه ممکن بود معلم کمتر از حقش تسویه شود.

## ۳) مسیر بررسی‌شده (خروج‌های زودهنگام، parse و فیلترها)

```
GET /teachers/{id}/pending_settlement
 ├─ گارد نقش: admin/secretary/teacher (معلم فقط خودش)         ← دست‌نخورده
 ├─ خروج زودهنگام ۱: معلم بدون کلاس ⇒ total 0 / count 0       ← دست‌نخورده
 ├─ خروج زودهنگام ۲: «هیچ جلسه‌ای در بازه نماند» ⇒ total 0     ← ★ اینجا باگ بود:
 │      چون فیلتر تاریخ، جلسه‌های بی‌تاریخ را حذف می‌کرد، اگر همه‌ی جلسه‌ها بی‌تاریخ بودند
 │      این خروج زودهنگام اجرا می‌شد و response صفر برمی‌گرداند.
 ├─ فیلتر جلسه‌ها: is_deleted=False + course_id های معلم        ← دست‌نخورده
 ├─ ★ فیلتر تاریخ (_in_range)                                  ← اصلاح شد
 ├─ فیلتر Attendance: is_billed=False، is_deleted=False، Present/Late  ← دست‌نخورده
 ├─ ساخت ردیف‌ها + شاخه‌ی penalty_only (جریمه‌ی غایبین)          ← دست‌نخورده (مبلغ تغییر نکرد)
 └─ مرتب‌سازی نهایی                                            ← deterministic شد
```

**نتیجه‌ی بررسی سایر مسیرها (بدون تغییر، فقط گزارش):**

- `routers/classes.py` (اثر حذف کلاس بر طلب معلم) → فیلتر تاریخ ندارد ⇒ سالم.
- `routers/analytics.py` (کیف پول معلم) و `routers/finance.py::teacher_settlements_summary` → فیلتر تاریخ ندارند ⇒ سالم.
- `routers/reports.py` (توابع `get_chart_data` و `get_financial_report`) → **همان الگوی `if parsed is None: return False`** را دارند؛ ولی این‌ها گزارش تقویمیِ تراکنش‌ها هستند نه طلب معلم — **طبق محدوده‌ی این Task تغییر نکردند** و برای تصمیم شما گزارش می‌شوند.

**نکته‌ی مدل داده:** ایندکس یکتا `uq_session_course_date_active` روی `(course_id, date)` برای ردیف‌های حذف‌نشده اعمال می‌شود. چون در SQL هر `NULL` یکتا حساب می‌شود، چند جلسه‌ی بی‌تاریخ در یک کلاس مجازند ولی تاریخ‌های معتبر تکراری مجاز نیستند (این محدودیت دست‌نخورده ماند و کمکی است به «جلسه دوباره ثبت نشود»).

## ۷) تصمیم‌ها و ریسک‌های باقی‌مانده (برای تصمیم شما)

1. **سیاست فیلتر بازه:** تصمیم این تسک این بود که جلسه‌های بدون تاریخ/نامعتبر **حتی وقتی بازه‌ی تاریخی درخواست می‌شود** هم حذف نشوند (چون نمی‌توان اثبات کرد بیرون بازه‌اند و حذفشان طلب را کم‌نمایش می‌کند). اگر ترجیح می‌دهید در حالت «بازه‌ی صریح» این جلسه‌ها کنار گذاشته شوند، یک خط تغییر است — بگویید.

3. **دو مسیر گزارش (`reports.py`)** همان الگوی حذفِ غیرقابل‌parse را دارند (چارت‌ها/گزارش مالی تراکنش‌ها). در این تسک تغییر نکردند چون خارج از محدوده بودند — اگر مایل باشید تسک جداگانه‌ای شود.
4. **بدون تغییر در اسکیمای دیتابیس و بدون migration**؛ فقط منطق خواندن اصلاح شد. هیچ رکوردی نوشته/به‌روزرسانی نشد (تست `test_16` این را قفل می‌کند).
5. **دامنه‌ی دسترسی** این اندپوینت تغییری نکرد: همان سه نقش مجاز و همان «معلم فقط خودش». (این اندپوینت از ابتدا فیلتر سطح-شعبه نداشت و اضافه‌کردنش یک تغییر رفتاری خارج از محدوده‌ی این تسک بود.)
