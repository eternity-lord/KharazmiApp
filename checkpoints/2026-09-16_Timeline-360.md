**Performance & N+1 Fix - 4 Queries (each limit 20) + merge/sort/slice 50:**

```python
# 1) Transactions - prevent N+1 for course_name (was 2N: query per txn + second for course title)
transactions = (
    db.query(Transaction)
    .options(joinedload(Transaction.course))  # 1 query JOIN courses, no per-row query
    .filter(Transaction.student_id==sid, Transaction.is_deleted==False, Transaction.is_reversed==False)
    .order_by(desc(Transaction.id)).limit(20).all()
)
# loop uses t.course.title already loaded, 0 extra queries

# 2) Attendance - prevent N+1 for session->course (was N+1 per attendance for SessionLog + Course)
attendances = (
    db.query(Attendance)
    .options(joinedload(Attendance.session).joinedload(SessionLog.course))  # 1 query JOIN session_logs + courses
    .filter(Attendance.student_id==sid, Attendance.status=="Absent")
    .order_by(desc(Attendance.id)).limit(20).all()
)
# loop uses att.session.course.title already loaded

# 3) Grades - prevent N+1 for course_name
grades = (
    db.query(Grade)
    .options(joinedload(Grade.course))  # 1 query JOIN courses
    .filter(Grade.student_id==sid)
    .order_by(desc(Grade.id)).limit(20).all()
)

# 4) Installments - via Enrollment join, joinedload to avoid N+1 for enrollment.course
installments = (
    db.query(Installment)
    .join(Enrollment, Installment.enrollment_id==Enrollment.id)
    .options(
        joinedload(Installment.enrollment).joinedload(Enrollment.course),
        joinedload(Installment.enrollment).joinedload(Enrollment.student),
    )
    .filter(Enrollment.student_id==sid, Enrollment.is_deleted==False, Installment.is_deleted==False)
    .order_by(desc(Installment.id)).limit(20).all()
)
# loop uses inst.enrollment.course.title already loaded
```

**Total Queries:** 1 (student exists check) + 4 (each limit 20) = **5 queries fixed**, regardless of student history size (vs N+1 which would be 20*N for 80 events). Verified in test: single timeline call emitted **5 SQL statements** (captured via `before_cursor_execute`).

```kotlin
private fun fetchTimeline() {
    tvTimelineEmpty.visibility = View.VISIBLE; tvTimelineEmpty.text = getString(R.string.timeline_loading)
    rvTimeline.visibility = View.GONE
    val api = RetrofitClient.getInstance(this).create(TimelineApi::class.java)
    lifecycleScope.launch(Dispatchers.IO) {
        try {
            val list = api.getTimeline(studentId)
            withContext(Dispatchers.Main) {
                if (list.isEmpty()) { tvTimelineEmpty.text = getString(R.string.timeline_empty); rvTimeline.visibility=GONE }
                else { tvTimelineEmpty.visibility=GONE; rvTimeline.visibility=VISIBLE; timelineAdapter?.update(list) }
            }
        } catch (e: Exception) {
            if (e is CancellationException) throw e
            withContext(Dispatchers.Main) { tvTimelineEmpty.text = getString(R.string.timeline_error, detail) }
        }
    }
}
```
Handles `CancellationException` correctly (not swallowed as network error), extracts server `detail` for 400/403/404 via `HttpException` JSON parsing, same pattern as A1 installments.

## 6. Design Rationale

- **N+1:** Each of 4 entities (Transaction, Attendance, Grade, Installment) previously required per-row JOIN to show course title (N extra queries). By adding `joinedload` with single JOIN, we fetch all needed course names in 1 query per entity. For Installment, join via Enrollment is required because Installment has no direct student_id; `joinedload(Enrollment.course)` avoids per-installment course lookup.
- **Performance:** 4*20 limit = max 80 rows in memory, merge sort 80 items is O(80 log 80) ~ negligible. 5 queries vs 80*N ensures <200ms even with cold DB. Slice 50 after sort ensures payload small (Android RecyclerView <50 items).
- **Isolation:** New router prevents regression in financial logic (finance hash proof). Models relationship addition is safe (lazy="select", no column change).
- **Security:** Reuse `check_student_access` (same as `students.py:310` for grades) ensures consistent policy for Admin/Secretary/Teacher/Parent roles, no new auth logic.
