## ۱) مشکل و ریشه

در ۵ فایل سرور، نام کامل افراد با الگوی زیر ساخته می‌شد:

```python
f"{obj.first_name} {obj.last_name}"
```

ستون‌های `first_name`/`last_name` در `models.py` برای `Student`، `Teacher` و `User` **nullable** هستند (رکوردهای legacy، ثبت نیمه‌کاره، وارد کردن دسته‌ای). نتیجه:

| حالت | خروجی قدیمی |
|---|---|
| هر دو NULL | `"None None"` |
| فقط نام NULL | `"None رضایی"` |
| فقط نام‌خانوادگی NULL | `"علی None"` |
| رشتهٔ خالی/فاصله | `"  "` یا `" علی "` با فاصله‌های اضافه |

این رشته‌ها فقط نمایشی نبودند: در **پاسخ API** (اپ اندروید)، **رسید و فاکتور چاپی**، **HTML گزارش**، **فایل اکسل**، **متن پیامک/اعلان** و حتی در **`User.full_name` سایهٔ معلم در `auth.py` ذخیره** می‌شدند — یعنی یک‌بار `"None None"` در دیتابیس می‌نشست و بعد در ورودهای بعدی هم تکرار می‌شد.

نقطهٔ حساس در `auth.py`: مقایسه/همگام‌سازی

```python
if u.full_name != f"{teacher.first_name} {teacher.last_name}":
    u.full_name = f"{teacher.first_name} {teacher.last_name}"
```

اینجا **دو طرف مقایسه باید دقیقاً یک مقدار بدهند**؛ در غیر این صورت هر لاگین یک `UPDATE` بی‌دلیل و نوسان نام است. این نوبت هر دو طرف را به یک مقدار مشترک (`_teacher_name`) تبدیل کرد.

## ۲) رفتار قبل و بعد

| نقطه | قبل | بعد |
|---|---|---|
| نام کامل شخص در پاسخ API/HTML/اکسل/پیامک | `"None None"` / `"None رضایی"` | `"علی رضایی"`؛ اگر هیچ بخشی نبود ⇒ جایگزینِ همان نقطه (`"نامشخص"`) |
| `User.full_name` سایهٔ معلم (auth) | `"None None"` | `"معلم"` (جایگزین) و در ورودهای بعدی **بی‌تغییر** |
| لاگین معلم بدون نام | `name: "None None"` | `name: "معلم"` (غیرخالی، بدون `None`) |
| دانش‌آموزِ موجود با نام NULL در جلسه | `"None None"` | `"نامشخص"` |
| دانش‌آموزی که **رکوردش نیست** | `"حذف شده"` | `"حذف شده"` (**بی‌تغییر** — تفکیک «رکورد نیست» از «نام ندارد») |
| کلاسی که **رکورد معلمش نیست** | `"نامشخص"` (classes/reports) و `"بدون معلم"` (finance) | همان، **بی‌تغییر** |
| اعدادی مثل طلب معلم، مبلغ رسید، جمع درآمد | — | **کاملاً بی‌تغییر** (تست‌شده) |

**قاعدهٔ جایگزین‌ها:** همان جایگزین‌های موجودِ هر نقطه حفظ شد؛ فقط جایی که شرط `if x else "<جایگزین رکورد-نیست>"` بود، «رکورد نیست» و «نام ندارد» از هم تفکیک شدند تا دانش‌آموزِ نام‌نداشته اشتباهاً «حذف شده» برچسب نگیرد (و برعکس).

## ۷) ریسک‌ها و محدودیت‌های باقی‌مانده

1. **نام‌های جایگزین ممکن است «نام واقعی» به‌نظر برسند** (`"نامشخص"`/`"حذف شده"`): این قرارداد موجود برنامه است و عمداً تغییر نکرد. اگر در آینده لازم شد «نام ناقص» از «رکورد ناموجود» در UI تفکیک شود، تغییر قرارداد API است و باید جداگانه تصمیم گرفته شود.
2. **`full_name`های قبلاً ذخیره‌شده در دیتابیس** (اگر جایی `"None None"` ماندگار شده باشد) با این تغییر **خودکار اصلاح نمی‌شوند** — فقط مسیرهای نوشتن آینده امن شدند. سنجش:
   ```sql
   SELECT id, username, full_name FROM users WHERE full_name LIKE '%None%';
   SELECT id, first_name, last_name FROM students WHERE first_name IS NULL OR last_name IS NULL;
   SELECT id, first_name, last_name FROM teachers WHERE first_name IS NULL OR last_name IS NULL;
   ```
   در دیتابیس فعلی پروژه (`Kharazmi_Server/gaj_db.db`) این ردیف‌ها در صورت وجود، خارج از دامنهٔ این نوبت باقی می‌مانند (مطابق قانون «یک تصمیم در هر نوبت»).
3. **شاخهٔ ادمین در لاگین** (بند ۵-۱) و **`InstituteSettings` خالی** (بند ۵-۲) دو مورد **مستندشده و باز** برای تصمیم‌های بعدی‌اند.
4. **۱۲ نقطه در `finance.py`** عمداً فقط جایگزینی متن بودند؛ هیچ فرمول مالی (سهم معلم/آموزشگاه، جریمه، تسویه، اقساط) لمس نشد — و این با تست‌های «عددِ بی‌تغییر» قفل شد.
